
> [!普通索引与唯一索引]
    > - 普通索引
    > 	- 最基本的索引类型，没有任何限制。
    > 	- 它唯一的作用是**加快数据的访问速度**
    > 	- 允许被索引的列包含重复的值
    > - 唯一索引
    > 	- 与普通索引类似，但有一个核心约束---**索引列的值必须是唯一的**
    > 	- 一个表可以有多个唯一索引
    > 	- 通常用于实现数据库的**唯一性约束**
    > 		- 当在一个列上创建了唯一性约束（`UNIQUE KEY` 或 `PRIMARY KEY`），数据库自动为该列创建一个唯一索引


- 当需要更新一个数据页时，如果数据页在内存中就直接更新
- 如果这个数据页还没有在内存中的话，在不影响数据一致性的前提下，InnoDB 会将这些<u>更新操作</u>缓存在 change buffer 中，这样就不需要从磁盘中读入这个数据页了。在下次查询需要访问这个数据页的时候，将数据页读入内存，然后执行 change buffer 中与这个页有关的操作
（这里说的数据页，是指二级索引树的数据页，并不是聚簇索引即主键树的数据页）

- 虽然名字叫作 change buffer，实际上它是可以持久化的数据
- <u>change buffer 在内存中有拷贝，也会被写入到磁盘上</u>

- 将 change buffer 中的操作应用到原数据页，得到最新结果的过程称为 <font color="#938953">merge</font>
- 执行merge的操作
	- 访问这个数据页
	- 系统有后台线程会定期 merge
	- 数据库正常关闭（shutdown）的过程中

如果能够将更新操作先记录在 change buffer，减少读磁盘，语句的执行速度会得到明显的提升。而且，数据读入内存是需要占用 buffer pool 的，所以这种方式还能够避免占用内存，提高内存利用率。


> [!SUMMARY]
    > ChangeBuffer 与索引类型的关系
    > - 普通索引   ✔️
    > 	- 可以使用 Change Buffer
    > 	- 普通索引可重复，即使不立即更新到数据页，也不会破坏数据一致性
    > - 唯一索引   ❌
    > 	- 不能使用 Change Buffer
    > 	- 每次插入或更新时，都必须立即判断是否违反了唯一性约束。
    > 		- 这个判断过程需要将数据页读入内存来检查。既然数据页已经在内存中了，那么更新操作就直接在内存中完成了

- change buffer 用的是 buffer pool 里的内存，因此不能无限增大。
- change buffer 的大小，可以通过参数 i`nnodb_change_buffer_max_size` 来动态设置。这个参数设置为 50 的时候，表示 change buffer 的大小最多只能占用 buffer pool 的 50%。


1. mysql数据存储在主键索引树的叶子节点。
2. 普通索引和唯一索引也都有自己的索引树，树的叶子节点存储的是主键ID。 
3. 做更新操作（插入，更新，删除）会同时更新所有的索引树结构。
	- 前提：**更新操作涉及到了这些索引的列**
> [!example]
> - `INSERT INTO t (id, name, email) VALUES (1, 'A', 'a@a.com');` 如果 id 是主键，name 上有普通索引，email 上有唯一索引，那么三个索引树都需要更新。
> -  `UPDATE t SET name = 'B' WHERE id = 1;` 修改了 name，所以需要更新 name 上的普通索引树。主键索引和 email 的唯一索引树不受影响。
> -  `UPDATE t SET email = 'b@b.com' WHERE id = 1;` 因为修改了 email，所以需要更新 email 上的唯一索引树。

- insert操作的影响大于update，如果有多个唯一索引，insert对内存命中率会有极大影响
	- 每个唯一索引在插入时都需要将其对应的索引页加载到内存（Buffer Pool）中进行检查。
	- 如果表有多个唯一索引，一次 INSERT 操作可能导致多次随机磁盘 I/O，将多个不同的索引页加载进内存。这会占用 Buffer Pool 空间，可能将其他常用数据页“挤出去”，从而降低内存命中率，影响整体性能

益处：
 1. 减少读磁盘：==仅仅是减少的是对二级普通索引页的读磁盘操作==，而对于其他类型的页(唯一索引，主键索引)还是要读磁盘的。 
 2. 减少内存占用：change buffer虽然还是需要内存占用(记录数据更新动作)，但相比于数据页来说(默认16K)，所占的内存还是小了很多的。


### 使用场景
普通索引的所有场景，使用 change buffer 都可以起到加速作用吗？

- <u>merge 的时候是真正进行数据更新的时刻</u>
- change buffer 的主要目的就是将记录的变更动作缓存下来，所以在一个数据页做 merge 之前，change buffer 记录的变更越多（也就是这个页面上要更新的次数越多），收益就越大。
- 因此，对于***写多读少***的业务来说，页面在写完以后马上被访问到的概率比较小，此时 change buffer 的使用效果最好。
	- 这种业务模型常见的就是<u>账单类、日志类</u>的系统。
