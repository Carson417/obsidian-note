### 只有一个索引
这里的“索引”指的就是 **Key**。

- 在关系型数据库（如 MySQL）中，你一张表可以有多个索引：主键索引、唯一索引、普通索引等。你可以根据 `id` 查，也可以根据 `name` 查，还可以根据 `create_time` 查。
- 但在纯粹的 KV 存储中，**有且仅有一个“入口”**，那就是 **Key**。你**只能通过这个 Key 来查找数据**。

**这意味着什么？**
- **访问模式单一**：你只能通过 `get(key)` 和 `put(key, value)` 来操作数据。
- **无法进行复杂查询**：你**不能**像 SQL 那样执行 `WHERE name = ‘Alice’` 或 `ORDER BY age DESC` 这样的查询。因为 `name` 和 `age` 这些字段没有被单独建立索引，它们只是 Value 的一部分。

**举例说明：**  
假设你在 KV 存储中存了一个用户数据：
- `Key: user_id_1001`
- `Value: {"name": "张三", "age": 28, "city": "北京"}`
- **你能做的**：通过 `get("user_id_1001")` 快速拿到整个用户信息。
- **你不能直接做的**：
    - “找出所有叫‘张三’的用户”（无法根据 `name` 查询）。
    - “找出所有在北京的用户”（无法根据 `city` 查询）。
    - “按年龄给用户排序”（无法根据 `age` 排序）。
要实现上述复杂查询，你必须在应用层自己处理（例如，扫描所有数据，这非常慢），或者建立额外的反向索引结构（例如，用另一个 KV 对 `name_张三: [user_id_1001, user_id_1002]` 来维护）。

---

### 该索引必须是唯一索引
“唯一索引”的意思是，**每一个 Key 在整个数据库中只能出现一次**。

- **保证唯一性**：就像每个人的身份证号是唯一的一样，每个 Key 也是唯一的。你不能用同一个 Key 存储两个不同的 Value。
- **覆盖写**：当你使用一个已经存在的 Key 去写入一个新的 Value 时，**新 Value 会直接覆盖掉旧的 Value**，而不会报错（除非你使用特殊的原子操作）。这个操作通常被称为 `put` 或 `set`。

**举例说明：**
1. 你执行 `put("counter", 10)`
2. 数据库里现在存在：`"counter" -> 10`
3. 你又执行 `put("counter", 20)`
4. 数据库里现在变成：`"counter" -> 20`。之前的值 `10` 被覆盖了，不复存在。
    
---

### 为什么这么设计？
这种看似“简陋”的设计，带来了两大核心优势：
1. **极致的性能**：因为数据结构简单，访问路径唯一，所以可以被优化到极致（尤其是内存型 KV 存储如 Redis），实现极高的吞吐量和极低的延迟。
2. **出色的可扩展性**：由于数据之间没有复杂的关联，可以通过对 Key 进行哈希分片的方式，非常容易地将数据分布到多台机器上，实现水平扩展。
    

***只有一个索引，该索引必须是唯一索引***就是在描述 ***KV 存储最基本、最核心的工作原则***。
